\section{Background and related work}
\label{sec:background}

\subsection{Authenticated encryption with associated data}

An authenticated-encryption scheme with associated data (AEAD) takes a key, a nonce, a plaintext and a string of associated data, and returns a ciphertext with an authentication tag. Decryption succeeds only if the key, nonce, ciphertext \emph{and} associated data are all presented unchanged; the associated data is authenticated but not encrypted, so it may be public~\cite{rogaway2002aead,rfc5116}. The two schemes in wide deployment are AES in Galois/Counter Mode~\cite{nist-gcm} and ChaCha20-Poly1305~\cite{rfc8439}; the XChaCha variant extends the latter's nonce to 192 bits so that random nonces are safe at any volume~\cite{xchacha-draft}. Bellare and Namprempre established the relations among the security notions and showed that encrypt-then-MAC is the sound generic composition~\cite{bellare2000ae}, which is why the shared-key baseline in Section~\ref{sec:evaluation} is built that way. Associated data is the standard mechanism for binding a ciphertext to the context in which it may be decrypted. In transport protocols it binds headers and sequence numbers; in storage encryption for clinical data it is largely unused, and when it is used, the content and encoding of the bound context are left to each application.

\subsection{Key derivation and key commitment}

Deriving many keys from one master key is the job of a key-derivation function. HKDF~\cite{rfc5869,krawczyk2010hkdf} extracts a pseudorandom key from input material and expands it under a label; distinct labels yield computationally independent keys. CPDPM uses the canonical context as part of the label, so every context has its own key. Where a master key must come from a password, Argon2id is the current recommendation~\cite{rfc9106}.

The standard AEAD schemes are not key-committing. Albertini et al.\ showed that a single AES-GCM or ChaCha20-Poly1305 ciphertext can be crafted to decrypt validly under two different keys, and that this enables practical attacks wherever the receiver may hold several candidate keys~\cite{albertini2022commitment}. Len, Grubbs and Ristenpart showed the consequence for password-derived keys: a partitioning oracle lets an attacker test many passwords per query~\cite{len2021partitioning}. The literature offers two responses: committing constructions~\cite{grubbs2017franking,bellare2022committing}, and the padding fix, a fixed derived value prepended to the plaintext and checked after decryption~\cite{albertini2022commitment}. CPDPM adopts the padding fix with a 32-byte HKDF-derived commitment, because it composes with any AEAD the underlying library provides.

\subsection{Encryption context in practice, and the database adversary}
\label{sec:practice}

Practice has converged on the idea this paper formalises for clinical records. AWS Key Management Service binds each key use to an ``encryption context'' of key-value pairs that must be supplied again at decryption~\cite{aws-kms-context}. Google's Tink library documents associated data as the way to bind a ciphertext to its intended location, with the example of a database row's primary key~\cite{tink-aead}. Neither prescribes \emph{what} to bind for a clinical record, nor an encoding under which two contexts cannot collide, nor a key hierarchy that isolates the blast radius of a leaked key; those are the design decisions of Section~\ref{sec:design}.

The closest industrial relative of those decisions is the AWS Database Encryption SDK~\cite{aws-dbesdk}, the client-side library formerly called the DynamoDB Encryption Client. It encrypts the attributes of a record under a data key fresh to that encryption, includes the table's logical name and the item's primary key values in an encryption context to which the record is bound, signs the record so that adding or deleting fields or swapping encrypted values is detected, and commits to the data key~\cite{aws-dbesdk-concepts}. Its hierarchical keyring derives wrapping keys from versioned branch keys held in a key store, one branch key per tenant in a multitenant schema~\cite{aws-dbesdk-hierarchical}. These are the same decisions Section~\ref{sec:design} makes, taken for a different data model: the SDK binds to a DynamoDB item's primary key rather than to a clinical context of patient, resource type and field path, and it is specific to DynamoDB. Section~\ref{sec:discussion} sets the two side by side.

The adversary that motivates them is the one the encrypted-database literature has studied for a decade. CryptDB made the case that a database server should be treated as untrusted and that encryption alone does not prevent it from serving wrong answers~\cite{popa2011cryptdb}. Grubbs, Ristenpart and Shmatikov distinguished the snapshot attacker, who sees the database once, from the persistent attacker, who observes and manipulates it over time, and argued that most encrypted-database security claims hold only against the former~\cite{grubbs2017encrypted-db}. The insider with write access in Section~\ref{sec:threat} is a persistent attacker whose goal is integrity of association rather than confidentiality: not to read a record but to relocate it.
