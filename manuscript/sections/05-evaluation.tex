Two experiments. The first asks whether the construction does what Section~\ref{sec:threat} says an adversary can do to the baselines. The second asks what it costs. Both run from the artifact with one command; payloads are FHIR \code{Observation} resources built from a public stroke-prediction dataset of 5{,}110 rows~\cite{kaggle-stroke}, which supplies realistic record shapes and sizes and nothing more.

\subsection{Record swap}
\label{sec:swap}

Three schemes are driven through one interface: the application encrypts one field of one resource for one patient in one tenant, stores the string, and later decrypts whatever it finds in that cell for the row it believes it is reading.

\begin{itemize}
  \item \textbf{AES-256-CBC with HMAC-SHA256 under one shared key}, random IV. A typical legacy design for encryption at rest.
  \item \textbf{AES-256-GCM with one key per tenant}, random nonce, no associated data. A typical modern design.
  \item \textbf{CPDPM}, AES-256-GCM suite.
\end{itemize}

Four manipulations by an adversary with database write access, illustrated in Figure~\ref{fig:record-swap}:
\begin{itemize}
  \item \emph{Patient swap.} Bob's ciphertext is copied into Alice's row; the application decrypts for Alice.
  \item \emph{Tenant move.} A ciphertext from tenant $P$ is stored in tenant $Q$'s table; the application decrypts for $Q$.
  \item \emph{Field move.} The ciphertext of the note field is written into the column for the effective date, so a value bound to \code{note[*].text} is read as \code{effectiveDateTime}.
  \item \emph{Stale replay after key retirement.} A ciphertext written before a key rotation is presented after the old key is retired. Only CPDPM has key versioning, so for the two baselines this column records a missing capability rather than a failed check.
\end{itemize}

Table~\ref{tab:swap} gives the result. The shared-key baseline accepts all three substitutions: its MAC proves the bytes were produced under the key, not that they belong to this row. The per-tenant baseline rejects only the tenant move, because the key differs, and accepts the other two. CPDPM rejects all three, and after retirement of the key version under which a ciphertext was written, rejects that ciphertext as well; the baselines have a single long-lived key, so a stale ciphertext under them stays valid indefinitely, and the column reports that as a capability difference rather than a failed check. The same swap driven through the FHIR layer, Bob's encrypted \code{Condition} stored in Alice's row and decrypted for Alice, is likewise \SwapFhir{}. Beyond the four manipulations, the manifest of Section~\ref{sec:fhir} detects deletion, reordering and duplication of encrypted fields and per-field replay within a resource; these are exercised in the test suite rather than repeated here.

Two honest notes. Per-tenant keys already stop the tenant move, so CPDPM's binding contribution is the patient-swap and field-move columns, and its retirement column is a key-management capability rather than a binding result. And retirement is not replay within a live key version; the latter is discussed in Section~\ref{sec:discussion}.

\subsection{Cost}
\label{sec:cost}

Encryption and decryption latency were measured with \code{pyperf} (eight processes, three values each, one warm-up) for FHIR bundles of 1, 10, 100 and 1{,}000 observations, from \BytesOne{} to \BytesThousand{} bytes, against three widely used libraries with pre-established keys and no password derivation on the hot path: raw AES-256-GCM from \code{cryptography}, Fernet, and Google Tink's AES-256-GCM. CPDPM was measured in both suites. The reported run is on \BenchPlatform{} under Python \BenchPython; the same suite was run on an x86-64 GitHub Actions runner (\XCpu) and is summarised below. Figures~\ref{fig:latency} and~\ref{fig:overhead} show the results.

CPDPM with AES-GCM carries a fixed cost of about \CpdpmFixedUs\,$\mu$s per operation: two HKDF derivations, the commitment, and header and context encoding. It then tracks raw AES-GCM. On a single \BytesOne-byte record it is \CpdpmRatioOne$\times$ the raw floor at \CpdpmUsOne\,$\mu$s; at \BytesHundred{} bytes it is \CpdpmRatioHundred$\times$; at \BytesThousand{} bytes it is \CpdpmRatioThousand$\times$. Fernet, the most common ``just encrypt it'' choice in Python, is \FernetRatioOne$\times$ at one record and \FernetRatioThousand$\times$ at a thousand, so CPDPM is faster than Fernet from ten records upward while binding what Fernet does not. Tink is faster than the raw baseline at small sizes because it caches the cipher object where the baseline constructs one per call, which is how application code typically behaves. The FHIR field-level path with three encrypted fields on one observation costs \FhirFieldsEncUs\,$\mu$s to encrypt and \FhirFieldsDecUs\,$\mu$s to decrypt, about 37\,$\mu$s per field including the manifest: per-field key derivation is the price of per-field binding.

The x86-64 run tells the same story with different constants: CPDPM with AES-GCM is \XCpdpmRatioOne$\times$ the raw floor at one record and \XCpdpmRatioThousand$\times$ at a thousand, a fixed cost of about \XCpdpmFixedUs\,$\mu$s, and Fernet is \XFernetRatioThousand$\times$ at a thousand.

One result needs a caveat. The XChaCha20-Poly1305 suite measures \XchachaRatioThousand$\times$ the raw floor at \BytesThousand{} bytes on the arm64 machine and \XXchachaRatioThousand$\times$ on x86-64. A direct comparison on the arm64 machine shows PyNaCl's bundled libsodium encrypting 670\,KB in about 10\,ms where OpenSSL's ChaCha20-Poly1305 takes 0.3\,ms and hardware-accelerated AES-GCM 0.07\,ms; the gap is the library build and the absence of hardware acceleration for ChaCha, not the construction. AES-GCM is the default suite for that reason, and a \code{cryptography}-backed ChaCha20-Poly1305 suite is the natural next addition.
